Developer field guide · offline · Python + SQLite

A to-do list that survives a worker disappearing.

Jobservice stores small automation jobs in a SQLite file. A worker takes one, runs a handler, and records its result. The durable version gives each attempt a time-limited claim, so the queue can recover if that worker crashes.

What changed?

Before, a crash after taking a job left it “running” forever. Now taking work creates an expiring lease and a fresh token. A replacement can retry abandoned work, while the old token cannot overwrite the replacement's result.

How does a lease work?

Imagine a checkout slip marked “valid until 10:00:30.” Before that time, the worker holding the current slip can renew it or finish. At exactly 10:00:30 the slip is invalid, even if no one has collected the overdue work yet. Another attempt gets a new slip, even if it uses the same worker name.

queued → claim → running → live completion → succeeded
                    │
                    ├─ failure / observed expiry → delayed queued retry
                    │                              or failed when exhausted
                    └─ cancel request → owner/reaper resolves → cancelled

The default retry delays are 1, 2, 4, … seconds, capped at 60. Claims count against the attempt limit, including claims by workers that crash. A failure or recovery starts its delay when it is observed. A worker poll never sleeps waiting for that future retry. See the full API contract.

Why “exactly once” needs a boundary

A worker could send an email and then crash before saving “done.” Its replacement may send it again. Database transitions and event commits are fenced and atomic; external effects remain at-least-once. Enqueue deduplication does not deduplicate handler effects. Use the downstream system's own idempotency key when a repeated effect would be harmful.

Use it

From the project root, submit and process one job. Repeating the submission with the same key and inputs returns the original job, including after success.

python3 -m jobservice --db demo.sqlite submit summary '{"values":[2,4,6]}' --idempotency-key report-7
python3 -m jobservice --db demo.sqlite work --once --lease-seconds 30
python3 -m jobservice --db demo.sqlite list --state succeeded
python3 -m jobservice --db demo.sqlite stats

Replace JOB_ID with a submitted id to inspect its events or request cancellation. Cancel stops queued work immediately; running code must cooperate.

python3 -m jobservice --db demo.sqlite events JOB_ID
python3 -m jobservice --db demo.sqlite cancel JOB_ID
python3 -m jobservice --db demo.sqlite reap
python3 -m unittest discover -s tests -v

Long-running custom handlers explicitly call context.heartbeat() or context.check_cancelled(). These renew the lease; the latter raises when a durable cancellation was requested. There is no background heartbeat. See ExecutionContext and the handler registry and built-ins.

What should a maintainer watch?

Use a local filesystem and consistent retry policy/clock across workers. Read APIs never recover work: a supervisor must issue another claim or explicit reap. Jobs, keys and events are not automatically pruned. Cancellation does not kill processes. Storage errors propagate instead of pretending the job finished.

Opening an older database migrates its schema atomically and preserves stored results and insertion order. Legacy running work has no valid owner and can be recovered. See Database initialization and architecture and failure boundaries.
